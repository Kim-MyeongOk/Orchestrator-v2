Git 커밋 메시지는 단순한 변경 이력을 넘어, 팀원 간의 소통과 코드 리뷰, 그리고 버그 추적을 위한 중요한 자산입니다. 글로벌 오픈소스 커뮤니티와 산업계에서 널리 쓰이는 **Conventional Commits(규약적 커밋)** 규칙을 기반으로 정의해 드립니다.

---

## 0. 커밋 작성자 (Author)

커밋 작성자 이름은 반드시 **`MyeongOk-Kim`** 으로 작성합니다.

```bash
git config user.name "MyeongOk-Kim"
```

* 저장소 단위로 위 명령을 실행해 두면 이후 모든 커밋의 작성자 이름이 통일됩니다.
* 이미 작성한 커밋의 작성자를 바꿔야 할 경우: `git commit --amend --author="MyeongOk-Kim <이메일>"`

---

## 1. 커밋 메시지 구조

커밋 메시지는 크게 **제목(Header), 본문(Body), 꼬리말(Footer)** 3가지 파트로 나뉩니다.

```text
<타입>(<스코프>): <제목>  <!-- 헤더 (필수) -->

<본문>                    <!-- 본문 (선택) -->

<꼬리말>                  <!-- 푸터 (선택) -->
```

---

## 2. 각 파트별 작성 규칙

### ① 타입 (Type) - 필수
커밋의 성격을 나타냅니다. 다음 중 하나를 선택합니다.

| 타입 | 설명 |
| :--- | :--- |
| **feat** | 새로운 기능 추가 (Feature) |
| **fix** | 버그 수정 (Bug Fix) |
| **docs** | 문서 수정 (README, 주석 등) |
| **style** | 코드 포맷팅, 세미콜론 누락 등 코드 변경이 없는 수정 (Style) |
| **refactor** | 코드 리팩토링 (기능 변화 없이 구조 개선) |
| **test** | 테스트 코드 추가/수정 (테스트 관련) |
| **chore** | 빌드 업무 수정, 패키지 매니저 설정 등 기타 잡일 |
| **perf** | 성능 개선 (Performance) |
| **ci** | CI/CD 설정 파일 수정 |
| **revert** | 이전 커밋으로 되돌리기 |

### ② 스코프 (Scope) - 선택
변경된 모듈이나 영역을 지정합니다. (예: `user`, `auth`, `api` 등)
* 형태: 괄호 `()` 로 감싸서 작성
* 예시: `feat: 소셜 로그인 기능 추가`

### ③ 제목 (Subject) - 필수
변경 사항에 대한 간결하고 명확한 요약입니다.
* **길이**: 50자 이내 (최대 72자)
* **어조**: 명령문(현재 시제)으로 작성. (예: "추가했다" X -> "추가" O)
* **대소문자**: 첫 글자는 대문자로 작성 (한글은 제외)
* **마침표**: 제목 끝에 마침표(`.`) 금지
* **접두사**: 타입과 제목 사이에는 콜론(`:`)과 공백 1칸을 둠

### ④ 본문 (Body) - 선택
제목만으로 설명이 부족할 때 작성합니다.
* **필수 사항**: 제목과 본문 사이에는 **빈 줄 1줄**을 반드시 넣어야 함.
* **내용**: 무엇(What)을 왜(Why) 변경했는지 상세히 설명. (어떻게(How)는 코드로 설명)
* **형태**: 한 줄당 72자 이내로 줄바꿈.
* **어조**: 명령문 현재 시제 유지.

### ⑤ 꼬리말 (Footer) - 선택
주로 이슈 트래커 ID 연동이나 주요 변경 사항(Breaking Change) 명시에 사용합니다.
* **빈 줄**: 본문과 꼬리말 사이에 **빈 줄 1줄**을 둠.
* **이슈 종료**: `Closes #이슈번호`, `Resolves #이슈번호`
* **주요 변경**: `BREAKING CHANGE: 변경 내용` (대문자 필수, 메이저 버전 업을 암시)

## 3. 커밋 메시지 작성 예시

### 예시 1: 기능 추가 (feat)
```text
feat(user-api): 회원가입 이메일 중복 검사 API 추가

회원가입 시 이미 가입된 이메일인지 확인하는 API를 추가함.
프론트엔드 요청으로 실시간 검증을 위해 별도 API로 구현.

Closes #42
```

### 예시 2: 버그 수정 (fix)
```text
fix: 로그인 시 비밀번호 특수문자 누락 버그 수정

비밀번호 내 특수문자가 URL 인코딩되지 않아 발생하는 401 에러 수정.
encodeURIComponent를 적용하여 해결.

Resolves #108
```

### 예시 3: 주요 변경 사항 (BREAKING CHANGE)
```text
feat(auth): JWT 토큰 만료 시간 단축

보안 강화를 위해 Access Token 만료 시간을 24시간에서 1시간으로 변경.
Refresh Token 로직이 도입되었으므로 프론트엔드 연동 작업이 필요함.

BREAKING CHANGE: Access Token 만료 시간이 1시간으로 단축됨. 토큰 갱신 로직 필수
```

## 4. 한국어 커밋 메시지 작성 팁

팀의 성향에 따라 영어와 한국어를 혼용하여 사용합니다.

1. **타입, 스코프는 영어로 유지**: `feat`, `fix` 등은 영어로 유지하여 자동화 도구(Changelog 생성기 등)가 인식할 수 있게 합니다.
2. **제목과 본문**:
   * **한글 사용 시**: "~함", "~추가" 등 간결한 명사형 종결어미를 사용합니다. (예: `feat: 로그인 버튼 클릭 이벤트 추가`)
   * **영어 사용 시**: 동사 원형으로 시작합니다. (예: `feat: add login button click event`)
3. **조사 주의**: 제목에 조사(을, 를, 이, 가)를 남발하면 길어지고 가독성이 떨어지므로, 핵심 키워드 위주로 작성합니다.

---

## 5. 왜 이 규칙을 따라야 할까요?

1. **가독성**: 커밋 히스토리를 훑어보기만 해도 어떤 작업이 있었는지 직관적으로 파악할 수 있습니다.
2. **자동화**: `feat`, `fix` 등의 타입과 `Closes #이슈번호`를 활용하면, 버전 번호(SemVer) 자동 증가나 릴리즈 노트(Changelog) 자동 생성이 가능합니다.
3. **코드 리뷰 용이**: 리뷰어가 커밋의 목적을 먼저 이해하고 코드를 볼 수 있어 리뷰 품질이 올라갑니다.

팀 내에서 위 규칙을 기반으로, "한글/영어 사용 여부", "이슈 트래커 연동 방식" 등 세부 사항만 조정하여 사용하시는 것을 권장합니다.
