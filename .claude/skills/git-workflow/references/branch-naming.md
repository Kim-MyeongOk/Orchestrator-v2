Git 브랜치 명명 규칙은 팀의 워크플로우(Git Flow, GitHub Flow 등)에 따라 달라질 수 있지만, 산업계에서 가장 널리 쓰이이고 협업에 유리한 **Git Flow 기반의 명명 규칙**을 정의해 드립니다.

커밋 메시지 규칙과 마찬가지로, 브랜치명만 봐도 **어떤 작업인지(타입), 어디에 쓰일 것인지(스코프), 이슈 번호는 무엇인지** 직관적으로 알 수 있는 것이 핵심입니다.

---

## 1. 브랜치 명명 기본 규칙 (공통)

1. **소문자 사용**: 대소문자 혼용은 운영체제(Windows, Mac, Linux) 간 충돌을 일으킬 수 있으므로 모두 소문자를 사용합니다.
2. **케밥 케이스(Kebab Case)**: 단어와 단어 사이는 하이픈(`-`)으로 연결합니다. (예: `user-login`)
3. **슬래시(`/`)로 계층 구분**: 브랜치의 목적을 그룹화하기 위해 슬래시를 사용합니다. (예: `feature/이슈번호-설명`)
4. **이슈 번호 포함**: 트래커(Jira, GitHub Issues 등)와의 연동을 위해 브랜치명에 이슈 번호를 반드시 포함합니다.
5. **간결함**: 브랜치명이 너무 길어지면 가독성이 떨어지므로, 핵심 키워드 위주로 짧게 작성합니다.

---

## 2. 브랜치 타입 및 접두어(Prefix)

가장 앞에 오는 접두어는 해당 브랜치의 성격을 나타냅니다.

| 브랜치 타입 | 설명 | 수명 |
| :--- | :--- | :--- |
| **`main`** | 배포 가능한 프로덕션 상태의 브랜치 | 영구 |
| **`develop`** | 다음 배포를 위한 개발 통합 브랜치 | 영구 |
| **`feature/`** | 새로운 기능을 개발하는 브랜치 | 일시적 (Merge 후 삭제) |
| **`bugfix/`** | 개발 중(`develop`) 발생한 버그를 수정하는 브랜치 | 일시적 |
| **`hotfix/`** | 프로덕션(`main`)에서 발생한 긴급 버그를 수정하는 브랜치 | 일시적 |
| **`release/`** | 배포를 준비하기 위한 브랜치 (버전 명시 등) | 일시적 |
| **`refactor/`** | 기능 변화 없이 코드 구조를 개선하는 브랜치 | 일시적 |
| **`chore/`** | 빌드 설정, 의존성 업데이트 등 잡일을 하는 브랜치 | 일시적 |
| **`docs/`** | 문서 작업만을 위한 브랜치 | 일시적 |

---

## 3. 브랜치명 작성 포맷

```text
{타입}/{이슈번호}-{간단한-설명}
```

* **타입**: 소문자로 작성 (feature, bugfix 등)
* **이슈번호**: Jira 티켓 번호나 GitHub Issue 번호 (예: 123, PROJ-456)
* **간단한 설명**: 작업 내용을 케밥 케이스로 작성

---

## 4. 브랜치명 작성 예시

### ✅ 좋은 예시
* `feature/42-social-login` (42번 이슈: 소셜 로그인 기능 추가)
* `bugfix/88-password-encoding` (88번 이슈: 비밀번호 인코딩 버그 수정)
* `hotfix/201-payment-error` (201번 이슈: 결제 에러 긴급 수정)
* `release/v1.2.0` (v1.2.0 버전 배포 준비)
* `refactor/15-user-service` (15번 이슈: 유저 서비스 리팩토링)
* `chore/update-spring-boot` (스프링부트 버전 업데이트 - 이슈 번호가 없을 경우 생략 가능)

### ❌ 나쁜 예시
* `feature/login` (이슈 번호 누락 -> 추적이 어려움)
* `Feature/SocialLogin` (대문자 사용, 카멜케이스 사용 -> OS 간 충돌 및 가독성 저하)
* `bugfix/버그수정` (너무 포괄적임, 무슨 버그인지 알 수 없음)
* `update` (목적을 알 수 없는 브랜치명)

## 5. 팀 워크플로우에 따른 운영 팁

### ① Jira 등을 사용하는 경우
Jira 브랜치 이름 생성 기능을 사용하면 보통 `{이슈키}-{이슈요약}` 형태로 나옵니다. 이를 Git 컨벤션에 맞게 변형하여 사용하는 것을 권장합니다.
* Jira 자동 제목: `PROJ-123 소셜 로그인 기능 추가`
* 적용 브랜치명: `feature/PROJ-123-social-login`

### ② 한국어 vs 영어
* 브랜치명에는 **영어** 사용을 강력히 권장합니다. 터미널 환경에서 한글 입력/삭제 시 커서가 꼬이는 문제가 자주 발생하며, 일부 CI/CD 도구나 쉘 스크립트에서 인코딩 문제를 일으킬 수 있습니다.

### ③ Merge 후 브랜치 삭제
`feature/`, `bugfix/` 등 일시적 브랜치는 PR(Pull Request)이 Merge 되는 즉시 원격 저장소(GitHub, GitLab 등)에서 삭제하여 브랜치가 지저분해지는 것을 방지합니다. (GitHub의 "Automatically delete head branches" 기능 활용 권장)

---

## 6. 커밋 메시지와의 연계

이전에 정의한 커밋 메시지 규칙과 브랜치 규칙이 만나면 완벽한 추적성을 확보할 수 있습니다.

1. **브랜치 생성**: `git checkout -b feature/42-social-login`
2. **커밋 작성**: `feat(auth): 카카오 소셜 로그인 추가` (본문에 `Closes #42` 포함)
3. **PR 생성**: PR 제목은 브랜치명이나 주요 커밋 메시지를 따라감
4. **Merge & 삭제**: `develop` 브랜치로 병합 후 `feature/42-social-login` 브랜치 삭제

이렇게 규칙을 통일하면, 누군가 `main` 브랜치의 커밋 히스토리를 볼 때 어떤 브랜치에서 어떤 이슈를 해결하기 위해 병합된 코드인지 한눈에 파악할 수 있습니다.
