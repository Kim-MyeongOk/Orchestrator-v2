# 멀티 에이전트 개요 (Multi-agent Overview)

원문 : https://docs.langchain.com/oss/python/langchain/multi-agent

멀티 에이전트 시스템은 복잡한 워크플로우를 처리하기 위해 특화된 컴포넌트들을 조율한다. 다만 모든 복잡한 작업에 멀티 에이전트가 필요한 것은 아니다. 적절한 (때로는 동적인) 도구와 프롬프트를 가진 단일 에이전트로도 비슷한 결과를 낼 수 있는 경우가 많다.

## 언제 멀티 에이전트가 필요한가

개발자가 "멀티 에이전트"가 필요하다고 말할 때, 보통 다음 중 하나 이상을 원하는 것이다.

- **컨텍스트 관리 (Context management)** : 모델의 컨텍스트 윈도우를 넘치게 하지 않으면서 특화된 지식을 제공한다. 컨텍스트가 무한하고 지연이 0이라면 모든 지식을 하나의 프롬프트에 넣을 수 있겠지만, 현실은 그렇지 않으므로 관련 정보만 선택적으로 노출하는 패턴이 필요하다.
- **분산 개발 (Distributed development)** : 서로 다른 팀이 독립적으로 기능을 개발/유지보수하고, 명확한 경계를 두고 더 큰 시스템으로 조합한다.
- **병렬화 (Parallelization)** : 서브태스크별로 특화된 워커를 생성하여 동시에 실행해 더 빠른 결과를 얻는다.

멀티 에이전트 패턴은 다음 상황에서 특히 유용하다.

- 단일 에이전트가 도구가 너무 많아 어떤 도구를 쓸지 잘못 판단할 때
- 작업이 긴 프롬프트와 도메인 특화 도구 등 방대한 컨텍스트를 가진 특화 지식을 요구할 때
- 특정 조건이 충족된 뒤에야 기능이 풀리는 순차적 제약을 강제해야 할 때

멀티 에이전트 설계의 핵심은 **컨텍스트 엔지니어링** — 각 에이전트가 무엇을 보는지 결정하는 것이다. 시스템 품질은 각 에이전트가 자기 작업에 맞는 올바른 데이터에 접근하도록 보장하는 데 달려 있다.

## 패턴 (Patterns)

| 패턴 | 동작 방식 | 참조 |
|---|---|---|
| **Subagents (서브에이전트)** | 메인 에이전트가 서브에이전트를 도구로 조율한다. 모든 라우팅이 메인 에이전트를 거치며, 언제 어떻게 각 서브에이전트를 호출할지 메인이 결정한다. | references/multi-agent-subagents.md |
| **Handoffs (핸드오프)** | 상태에 따라 동작이 동적으로 바뀐다. 도구 호출이 상태 변수를 갱신하고 그것이 라우팅/설정 변경을 트리거하여 에이전트를 전환하거나 현재 에이전트의 도구·프롬프트를 조정한다. | references/multi-agent-handoffs.md |
| **Skills (스킬)** | 특화 프롬프트와 지식을 온디맨드로 로드한다. 단일 에이전트가 제어를 유지하면서 필요할 때 스킬에서 컨텍스트를 불러온다. | references/multi-agent-skills.md |
| **Router (라우터)** | 라우팅 단계가 입력을 분류하여 하나 이상의 특화 에이전트로 보낸다. 결과는 합쳐진 응답으로 종합된다. | references/multi-agent-router.md |
| **Custom workflow (커스텀 워크플로우)** | LangGraph로 맞춤형 실행 흐름을 만든다. 결정론적 로직과 에이전트 동작을 섞고, 다른 패턴을 노드로 임베드한다. | references/multi-agent-custom-workflow.md |

### 패턴 선택 기준

| 패턴 | 분산 개발 | 병렬화 | 멀티홉 | 직접 사용자 상호작용 |
|---|---|---|---|---|
| Subagents | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐ |
| Handoffs | - | - | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| Skills | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| Router | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | - | ⭐⭐⭐ |

- **분산 개발** : 서로 다른 팀이 컴포넌트를 독립적으로 유지보수할 수 있는가?
- **병렬화** : 여러 에이전트를 동시에 실행할 수 있는가?
- **멀티홉** : 여러 서브에이전트를 직렬로 호출하는 것을 지원하는가?
- **직접 사용자 상호작용** : 서브에이전트가 사용자와 직접 대화할 수 있는가?

패턴은 혼합할 수 있다. 예를 들어 Subagents 아키텍처가 커스텀 워크플로우나 라우터 에이전트를 호출하는 도구를 부를 수 있고, 서브에이전트가 Skills 패턴으로 온디맨드 컨텍스트를 로드할 수도 있다.

## 성능 비교

서로 다른 패턴은 서로 다른 성능 특성을 가진다.

- **모델 호출 수 (Model calls)** : LLM 호출 횟수. 호출이 많을수록 (특히 직렬이면) 지연과 요청당 API 비용이 커진다.
- **처리 토큰 수 (Tokens processed)** : 모든 호출에 걸친 총 컨텍스트 윈도우 사용량. 토큰이 많을수록 처리 비용과 컨텍스트 한계 위험이 커진다.

### 단발 요청 ("Buy coffee")

| 패턴 | 모델 호출 | 적합 |
|---|---|---|
| Subagents | 4 | |
| Handoffs | 3 | ✅ |
| Skills | 3 | ✅ |
| Router | 3 | ✅ |

핵심 : Handoffs, Skills, Router가 단일 작업에 가장 효율적(각 3회). Subagents는 결과가 메인 에이전트를 거쳐 돌아오기 때문에 호출이 1회 더 든다. 이 오버헤드는 중앙집중 제어를 제공한다.

### 반복 요청 (Turn 1 "Buy coffee", Turn 2 "Buy coffee again")

| 패턴 | Turn 2 호출 | 양 턴 합계 | 적합 |
|---|---|---|---|
| Subagents | 4 | 8 | |
| Handoffs | 2 | 5 | ✅ |
| Skills | 2 | 5 | ✅ |
| Router | 3 | 6 | |

핵심 : 상태를 유지하는 패턴(Handoffs, Skills)은 반복 요청에서 호출의 40~50%를 절약한다. Subagents는 무상태 설계라 강한 컨텍스트 격리를 주지만 요청당 비용이 일정하게 반복된다.

### 멀티 도메인 ("Compare Python, JavaScript, and Rust for web development")

각 언어 에이전트/스킬이 약 2000 토큰의 문서를 포함하고 모든 패턴이 병렬 도구 호출을 할 수 있다고 가정.

| 패턴 | 모델 호출 | 총 토큰 | 적합 |
|---|---|---|---|
| Subagents | 5 | ~9K | ✅ |
| Handoffs | 7+ | ~14K+ | |
| Skills | 3 | ~15K | |
| Router | 5 | ~9K | ✅ |

핵심 : 멀티 도메인 작업에서는 병렬 실행 패턴(Subagents, Router)이 가장 효율적이다. Skills는 호출 수는 적지만 컨텍스트 누적으로 토큰 사용량이 높다. Handoffs는 직렬 실행이 강제되어 여러 도메인을 동시에 조회하는 병렬 도구 호출을 활용할 수 없어 비효율적이다.

LangChain의 내장 멀티 에이전트 지원으로는 **Deep Agents**가 있다. 이는 LangChain 위에 구축된 상위 수준 하니스로 서브에이전트, 스킬, 플래닝, 가상 파일시스템, 컨텍스트 관리를 기본 제공한다.
